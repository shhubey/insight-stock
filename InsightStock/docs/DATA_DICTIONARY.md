# Snapshot data dictionary

One row represents a product variant, sales cohort and snapshot date. Counts are aggregates, not individual orders or customers. The CSV has 20 source fields; the database adds id.

| Field | PostgreSQL type | Meaning |
| --- | --- | --- |
| id | bigint identity | Database-generated internal snapshot key; not in the CSV. |
| record_id | text | Synthetic snapshot label, DEMO-01 through DEMO-09. |
| sku | text | Sales-side variant identifier. |
| product | text | Product name. |
| variant | text | Size, colour or other variant label. |
| return_sku | text | Return-side variant identifier; must match sales SKU for historical analysis. |
| sold_eligible_90d | integer | Eligible sold units in the 90-day sales cohort; denominator. |
| returned_in_30d_window | integer / NULL | Returned units from that cohort within the return window. NULL means unknown. |
| negative_review_mentions | integer | Number of synthetic reviews mentioning a complaint. |
| total_reviews | integer | Total reviews in the recorded review period; complaint-share denominator. |
| main_reason | text | Synthetic issue label; not generated by an AI classifier. |
| stock_on_hand | integer | Units in stock; operational exposure, not predicted returns. |
| cohort_start_date | date | First sales-cohort day (inclusive). |
| cohort_end_date | date | Last sales-cohort day (inclusive). |
| snapshot_date | date | As-of date for checking whether the cohort return window closed. |
| review_start_date | date | Beginning of the review period. |
| review_end_date | date | End of the review period. |
| return_window_days | integer | Demonstration policy window, 30 days. |
| review_excerpt_1 | text | Synthetic example review text. |
| review_excerpt_2 | text | Second synthetic example review text. |
| source | text | Synthetic source marker. |

Derived fields include history_status, review_status, historical_return_rate_pct, complaint_share_pct, risk_category, complaint_warning, rule_version and input_fingerprint. Validation returns one main blocking reason. Check database/01_analysis_and_decisions.sql for precedence.

manager_decisions stores owner, snapshot ID, input/rule version, server-captured input/evidence, action, note, responsibility and timestamp. Uniqueness is owner + snapshot + input fingerprint + rule version.

decision_followups stores the decision ID (primary key), copied product/SKU/action/note/responsibility/risk, NEW status, creation time and nullable notification timestamp. A task remains pending for notifications while notified_at is NULL. This timestamp is an acknowledgment after send, not an independently verified Telegram delivery receipt.
